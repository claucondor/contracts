# v0.6.6 Audit Report
Date: 2026-06-03

## Root Cause of C_old Mismatch (Legacy State)

The existing JanusFlow proxy and JanusERC20 proxy both have corrupted shielded state:

### JanusERC20 proxy
- `totalLocked = 70 mUSDC` but `underlying.balanceOf(proxy) = 0` (drained)
- Cause: v0.5 upgrade left storage inconsistent — the upgrade tx may have run wrap
  operations that moved funds without correctly updating totalLocked, or the proxy
  received a direct ERC20 transfer that was counted before the upgrade.
- **NOT FIXABLE without a fresh deploy + full re-accounting.**

### JanusFlow proxy
- Operator COA commitment = `(1.163e76, 1.402e76)` — non-identity, meaning some
  prior wrap did execute and store a commitment.
- `shieldedTransfer` reverts with `C_old mismatch` because the SDK's locally computed
  publicInputs[0,1] don't match the on-chain commitment.
- Root cause: the wrap that created the on-chain commitment used a blinding/amount
  that the SDK no longer knows about (snapshot was not persisted or the snapshot
  encryption was to a stale memokey). The SDK cannot reconstruct the correct
  (balance, blinding) pair for the existing commitment.
- **NOT FIXABLE without adminResetSlot + re-wrap from fresh state.**

## SDK Commitment Correctness Analysis

### Circuit: confidential_transfer.circom
- Pedersen(192) = 64-bit value || 128-bit blinding (little-endian byte packing)
- `computeCommitment` in `primitives/pedersen.ts` uses a 24-byte buffer: bytes[0..7]
  = value LE-8, bytes[8..23] = blinding LE-16 → **CORRECT for v0.3 circuits.**
- `computeCommitmentV05` (32-byte, 128-bit value) is documented but NOT used by any
  proof builders. The circuit does NOT match v0.5 docs — the actual circuit is v0.3.
- **No SDK commitment bug for fresh state.**

### Commitment flow after fresh wrap:
1. `orchestrateWrap(grossAmount, feeBps, senderMemoKeypair)`
   → `buildAmountDiscloseProof({amount: netAmount, blinding})`
   → `computeCommitment(netAmount, blinding)` → `txCommit = (Cx, Cy)`
2. Contract: `_acceptShieldedCredit` → `babyAdd(identity=(0,1), txCommit) = txCommit`
   → `commitments[msg.sender] = txCommit` ✓
3. `orchestrateShieldedTransfer(currentBalance=netAmount, currentBlinding=blinding, ...)`
   → `buildShieldedTransferProof({oldBalance=netAmount, oldBlinding=blinding})`
   → `computeCommitment(netAmount, blinding) = old_commit = txCommit` ✓ matches chain.

**Conclusion: SDK is correct for fresh deployments.**

## Architecture Discrepancy: Two JanusToken.sol Bases

- `packages/janus-token/contracts/solidity/JanusToken.sol` = v0.6.3 base
  (slots 0-10 + gap[79] + memoRegistry@slot90)
- `packages/janus-erc20/contracts/solidity/JanusToken.sol` = v0.3 base
  (slots 50-52 + commitments + totalSupplyCommitment + totalLocked + gap[40])

The two packages use DIFFERENT JanusToken base contracts. JanusERC20 stores
`memoRegistry` at slot 51 (its own storage), not slot 90 (base gap tail).
JanusFlow stores `memoRegistry` at slot 90.

For the v0.6.6 clean redeploy, this is acceptable — both deploy fresh with
known-good state. No upgrade compatibility needed.

## Decision: CLEAN REDEPLOY

Rationale:
1. JanusERC20 state is corrupted (totalLocked/balance mismatch).
2. JanusFlow operator state is corrupted (unknown blinding).
3. Operator explicitly requested fresh testnet account.
4. Fresh deploy with known-good state + correct SDK = no bugs.
