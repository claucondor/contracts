# v0.8 Demo Catalog — What's Buildable Fast

> Generated: 2026-06-10
> Reference: v0.8.1 protocol stack on Flow testnet (feat/shielded-recovery)
> Purpose: identify next demos using validated primitives with minimal new contract work

---

## Top 3 Recommendations

### Pick 1 — PrivateSplit (zero new contracts, ~1.5 weeks)

Split a bill among N people. Payer wraps once, sends N sequential `shieldedTransfer` calls — each recipient drains their inbox and sees only their share. No new contract, no new circuit. Stretches the inbox-as-private-delivery-channel primitive in a way that is immediately legible to non-crypto audiences ("privacy-native Venmo split"). Each transfer carries a schema extension: `split_id`, `total_splits`, `split_index`. 

### Pick 2 — PrivatePayroll (JanusERC20 path, ~2 weeks)

Employer holds shielded mUSDC. Every pay cycle, employer runs N `shieldedTransfer` calls and updates their `ShieldedCheckpoint` after each. Each employee drains their inbox and sees their salary and period. This is the first demo that uses the ERC20 path and the first that showcases the employer-side Checkpoint as a running ledger — not just a recovery tool. Recurring nature means it compounds well for demos (run it monthly, show the checkpoint advancing).

### Pick 3 — SealedVoting (one new contract, ~2.5 weeks)

Token-weighted proposal vote where individual weights are hidden until the ballot closes. Voters wrap FLOW → submit commitment to a `VoteCoordinator` contract → at reveal phase they submit amount-disclose proofs on-chain. The contract tallies and declares the result. Requires one new Solidity contract (~90 LOC) calling the already-deployed `AmountDiscloseAggregateVerifier`. No new circuit. Highest "tweets well" score and the clearest illustration that hidden amounts do not mean unintelligible tallying.

### Demo 1: PrivateSplit

**Tagline**: split a dinner bill with on-chain privacy — each person sees only their share.

**User story**:
- As the payer at a group dinner, I want to send each friend their exact share so that nobody knows what anyone else paid or what my total was.

**Privacy guarantee**:
- Hidden: individual split amounts per recipient; payer's total wrapped amount
- Revealed: payer address (msg.sender in ShieldedTransferNote events), recipient addresses, number of transfers, that a split event occurred

**Primitives used**:
- `wrapWithProof` — JanusFlow (payer wraps total)
- N × `shieldedTransfer` — one per recipient (sequential, same payer state machine)
- `ShieldedInbox.drainBatch` — each recipient claims their note
- ECIES encrypt/decrypt — per-recipient payload with split metadata
- `ShieldedCheckpoint.update` — payer updates checkpoint after each transfer

**New contract needed?**
- No. Plain JanusFlow EVM. Optional: a thin SplitRegistry Cadence contract (~30 LOC) to emit a `SplitCreated(splitId, payerAddr, recipientCount)` event for indexing. No new circuit.

**Schema for ECIES payload (app-defined)**:
```json
{"v":1,"amt":"X","bld":"Y","memo":"dinner:2026-06-10:trattoria-roma","split_id":"abc123","total_splits":4,"split_index":1}
```

**Front views (if we ship)**:
- `/split/create` — enter total, list of addresses and amounts per person, trigger proofs + transfers
- `/split/[id]` — public page showing split exists (no amounts), list of recipients
- `/inbox` — recipient view: drains inbox, shows "you received your share of split abc123"

**Effort estimate**:
- Contract (Cadence optional registry): 0–4 hours
- Scripts (.cjs): ~10 hours (wrap, N-transfer loop, checkpoint after each, per-recipient inbox claim)
- Frontend: 3 days

**Why it works with our stack**:
- A split is exactly N independent shieldedTransfers from one payer. The payer's commitment updates after each one (C_old → C_new per hop). The inbox delivers a separate note to each recipient. The only complexity is tracking the payer's evolving blinding between transfers — ShieldedCheckpoint handles that cleanly. The schema extension fields (`split_id`, `split_index`) are ignored by the contract and carried transparently through ECIES.

**What we'd need beyond v0.8.1**:
- Nothing. All there.

**Risk / unknowns**:
- If N is large (>10), the sequential proof-build + transfer loop takes minutes browser-side; move proof generation to `/api/proof/shielded-transfer` server route as PrivateTip does.
- Payer must track intermediate state carefully between transfers; if a transfer reverts mid-split, the payer's commitment may be partially advanced.

### Demo 2: AnonymousDonation

**Tagline**: donate to a campaign where your amount is private but the total raised is fully public.

**User story**:
- As a donor supporting a controversial cause, I want my donation amount to be invisible on-chain so that my financial support is not weaponized against me.

**Privacy guarantee**:
- Hidden: individual donation amounts (each donor's committed amount is opaque)
- Revealed: donor address (ShieldedTransferNote event `from` field), that a donation happened, aggregate total raised (via `JanusERC20.totalLocked()`)

**Primitives used**:
- `wrapWithProof` — JanusERC20 (mUSDC) — each donor wraps their amount
- `shieldedTransfer` — donor → campaign treasury EVM address
- `ShieldedInbox.drainBatch` — treasury owner drains to see individual amounts off-chain
- ECIES encrypt/decrypt — donor message in payload
- `MemoKeyRegistry.getMemoKey` — treasury publishes BabyJub pubkey; donors encrypt to it

**New contract needed?**
- No. The campaign treasury is a plain EVM address that has registered a BabyJub pubkey on MemoKeyRegistry. No new contract needed for the core flow. Optional: a thin `CampaignRegistry.sol` (~60 LOC) to maintain a list of campaigns with goals and deadlines — no new circuit.

**Schema for ECIES payload (app-defined)**:
```json
{"v":1,"amt":"X","bld":"Y","memo":"for:ocean-cleanup-fund","message":"keep going","anonymous":true}
```

**Front views (if we ship)**:
- `/campaign/[id]` — public: total raised (from `totalLocked`), donor count (from inbox note count), goal bar; no individual amounts
- `/donate` — donor view: wrap mUSDC, shieldedTransfer to campaign, optional message
- `/campaign/[id]/manage` — treasury owner only: drain inbox, see breakdown per donor, trigger unwrap when ready

**Effort estimate**:
- Contract: 0 hours (or 4h for optional CampaignRegistry)
- Scripts (.cjs): ~8 hours (mUSDC approve + wrap, transfer to campaign, treasury drain + decode)
- Frontend: 3 days

**Why it works with our stack**:
- `totalLocked()` is a public view that reveals the aggregate without any individual disclosure. Each donor's commitment accumulates homomorphically into the treasury's commitment. The treasury owner recovers individual amounts by draining and ECIES-decoding their inbox. This is a perfect demonstration of the homomorphic property: the sum is public, the parts are private.

**What we'd need beyond v0.8.1**:
- Nothing for core flow. ERC20 `approve` step must be handled in the UI (standard, already done in mUSDC smoke tests).

**Risk / unknowns**:
- Donor wallet addresses are visible in events; this demo hides amounts but NOT identity. Framing must be explicit: "amount-private donation," not "anonymous donation."
- Treasury unwrap at campaign end requires two proofs (amount-disclose + transfer); same as standard unwrap.

### Demo 3: PrivatePayroll

**Tagline**: pay your team in USDC with salaries that are invisible to competitors and colleagues.

**User story**:
- As an employer, I want to run payroll so that individual compensation is hidden from the blockchain while I retain a private record of what I paid each person.

**Privacy guarantee**:
- Hidden: each employee's salary amount; employer's total payroll outflow (locked in commitment until unwrap)
- Revealed: employer address, employee addresses, that payroll ran (event exists), period (in memo)

**Primitives used**:
- `wrapWithProof` — JanusERC20 (mUSDC): employer wraps payroll tranche
- N × `shieldedTransfer` — employer → each employee
- `ShieldedCheckpoint.update` — employer updates after each transfer (running balance)
- `ShieldedInbox.drainBatch` — each employee claims their paycheck note
- `BatchClaimClient.buildBatchClaimProof` — employer consolidates inbox if they receive wrap-back or test notes (experimental, clearly labeled)
- ECIES encrypt/decrypt — paycheck payload with period + department

**New contract needed?**
- No. JanusERC20 + existing primitives cover the full flow.

**Schema for ECIES payload (app-defined)**:
```json
{"v":1,"amt":"X","bld":"Y","memo":"payroll:2026-06","period":"2026-06","dept":"engineering","employee_ref":"E-001"}
```

**Front views (if we ship)**:
- `/payroll/run` — employer view: upload CSV (address, amount), trigger batch proofs + transfers, show checkpoint version advancing
- `/payroll/history` — employer only: shows past payroll runs with dates, employee count, total amount (decrypted from own checkpoint history)
- `/paycheck` — employee view: drain inbox, see paychecks by period

**Effort estimate**:
- Contract: 0 hours
- Scripts (.cjs): ~12 hours (ERC20 approve, wrap, N-transfer loop with checkpoint after each, employee drain + decode, per-period aggregation)
- Frontend: 4 days

**Why it works with our stack**:
- This is the first recurring demo. The employer's checkpoint advances every pay cycle, creating a natural audit trail that only the employer can read. The ERC20 path demonstrates that the protocol works with stablecoins, which is the realistic payroll token. The `ShieldedCheckpoint` version counter visibly advances each run, making the "running ledger" concept concrete.

**What we'd need beyond v0.8.1**:
- Nothing. JanusERC20 + ShieldedCheckpoint + ShieldedInbox are all deployed.

**Risk / unknowns**:
- Employer must approve JanusERC20 proxy for the full payroll tranche before the wrap. UI must surface this as a step.
- If the employer's blinding accumulates past the blinding overflow threshold across many pay cycles (unlikely within a single tranche but possible with many small wraps), `batchClaim` is needed to reset — this is experimental and labeled as testnet-only.

### Demo 4: SealedBidNFT

**Tagline**: bid on an NFT with a hidden amount — nobody knows how much you want it.

**User story**:
- As a bidder, I want to submit my max bid so that no one can front-run or shade my bid strategy during the auction.

**Privacy guarantee**:
- Hidden: each bidder's exact bid amount during the bidding phase
- Revealed: that a bid was placed (event exists + bidder address), each bid amount at reveal (bidder submits amount-disclose proof), winner and winning amount after settlement

**Primitives used**:
- `wrapWithProof` — JanusFlow: each bidder wraps their bid amount
- `AmountDiscloseAggregateVerifier.verifyProof` — called directly by `SealedBidAuction` at reveal phase
- `ShieldedCheckpoint` — bidder can recover their state if they need to re-prove

**New contract needed?**
- **Yes**: `SealedBidAuction.sol` ~180 LOC
  - Stores the NFT (ERC721 custody)
  - Phase management: `BIDDING → REVEAL → SETTLED`
  - `submitBid(commitment[2])` — stores bidder's Pedersen commitment during bid phase
  - `revealBid(publicInputs[4], proof[8])` — calls `AmountDiscloseAggregateVerifier.verifyProof`; records revealed amount
  - `settle()` — finds highest revealed amount, transfers NFT to winner, marks auction closed
  - Requires AmountDiscloseAggregateVerifier at `0xf7B634D41259D0613345633eE1CD193A030A6329`
  - **No new circuit** — calls the already-deployed verifier
  - ~180 LOC total

**Schema for ECIES payload (app-defined)**:
- Bidder encrypts their own state to themselves (standard self-checkpoint); no note to auctioneer
- The bid commitment itself is the only on-chain artifact

**Front views (if we ship)**:
- `/auction/[id]` — public: NFT details, bid count, time remaining, current phase
- `/auction/[id]/bid` — bidder: wrap FLOW, submit commitment
- `/auction/[id]/reveal` — bidder: submit amount-disclose proof to reveal their bid
- `/auction/[id]/result` — public: winner address, winning bid (post-settlement)

**Effort estimate**:
- Contract (Solidity): ~16 hours (phase logic, NFT custody, verifier integration, edge cases)
- Scripts (.cjs): ~12 hours (bidder wrap + commitment, reveal proof build + submit, settle call)
- Frontend: 5 days

**Why it works with our stack**:
- `AmountDiscloseAggregateVerifier` is already deployed. `SealedBidAuction` calls it directly — no proxy or proxy upgrade needed. The commitment submitted during bid phase uses the same Pedersen scheme as the `wrapWithProof` flow; the bidder just stores the commitment in the auction contract instead of the token contract. At reveal, the bidder submits a standard amount-disclose proof with `nonce=0` (the auction contract enforces reveal-phase uniqueness via the commitment stored at bid time).

**What we'd need beyond v0.8.1**:
- `SealedBidAuction.sol` (new contract, no new circuit)

**Risk / unknowns**:
- A bidder who does not reveal by the deadline forfeits their bid commitment (and their wrapped FLOW is trapped until the auction owner provides an escape hatch, or they use `adminBatchResetSlots` on testnet). This requires a clear UI warning.
- The NFT must be an ERC721 on Flow EVM. If using a Cadence NFT, a cross-VM bridge or COA ownership pattern is needed — significant additional complexity.

### Demo 5: SealedVoting

**Tagline**: vote on a proposal with your token weight hidden until the ballot closes.

**User story**:
- As a token holder, I want to vote on a governance proposal so that my voting weight is private during the voting period and cannot influence other voters.

**Privacy guarantee**:
- Hidden: each voter's weight during the voting phase
- Revealed: that a voter participated (their address), their weight and chosen option at reveal, the final tally (on-chain)

**Primitives used**:
- `wrapWithProof` — JanusFlow: voter wraps their voting tokens as a commitment
- `AmountDiscloseAggregateVerifier.verifyProof` — called by `VoteCoordinator` at reveal
- `ShieldedCheckpoint` — voter stores state for self-recovery between vote and reveal phases

**New contract needed?**
- **Yes**: `VoteCoordinator.sol` ~90 LOC
  - `createProposal(description, votingDeadline, revealDeadline)` — stores proposal
  - `submitVote(proposalId, option, commitment[2])` — BIDDING phase: stores commitment per voter per option
  - `revealVote(proposalId, publicInputs[4], proof[8])` — calls `AmountDiscloseAggregateVerifier`; tallies to the option the voter chose (stored at vote time)
  - `finalize(proposalId)` — computes winner after reveal deadline
  - **No new circuit** — calls already-deployed verifier

**Schema for ECIES payload (app-defined)**:
- Voter ECIES-encrypts their own vote state to themselves (standard checkpoint pattern): `{v:1, amt:"W", bld:"Y", memo:"vote:PROP-001:yes"}`
- Nothing sent to the contract via ECIES — the commitment is the on-chain artifact

**Front views (if we ship)**:
- `/vote/[id]` — public: proposal text, yes/no commitments count, phase indicator, time remaining
- `/vote/[id]/submit` — voter: wrap tokens, choose yes/no, submit commitment
- `/vote/[id]/reveal` — voter: submit amount-disclose proof to disclose their weight
- `/vote/[id]/results` — public: final tally breakdown (post-finalize)

**Effort estimate**:
- Contract (Solidity): ~10 hours (phase logic, verifier call, tally, finalize)
- Scripts (.cdc/.cjs): ~10 hours (wrap, commit submit, reveal proof build + submit, finalize, read results)
- Frontend: 4 days

**Why it works with our stack**:
- `AmountDiscloseAggregateVerifier` is immutable and already deployed. `VoteCoordinator` calls it directly at reveal. The voter's weight is a Pedersen commitment that the verifier validates against the disclosed amount — the same math used in every wrap operation. The phase management is purely Solidity state machine logic. The checkpoint demo is natural here: a voter may wrap days before the reveal deadline, so `ShieldedCheckpoint` provides the recovery story if they switch devices.

**What we'd need beyond v0.8.1**:
- `VoteCoordinator.sol` (new contract, no new circuit)

**Risk / unknowns**:
- A voter who wraps but never reveals is counted as abstain; their FLOW stays in JanusFlow. This needs an explicit escape (allow unwrap after reveal deadline regardless of reveal status).
- Vote-buying risk: if a voter reveals early, their weight is known — frontends should encourage voters to wait until reveal deadline before revealing.

### Demo 8: HiddenLeaderboard

**Tagline**: compete in a game where scores are sealed during the season; rank is public but exact values hidden until reveal.

**User story**:
- As a competitive player, I want my score hidden during the season so that I cannot be targeted for harassment based on my exact standing.

**Privacy guarantee**:
- Hidden: exact score during the season (stored as Pedersen commitment)
- Revealed: rank ordering (derived at season-end from amount-disclose proofs), exact scores after reveal

**Primitives used**:
- `wrapWithProof` / commitment submission — player submits a Pedersen commitment of their score to a `LeaderboardCoordinator`
- `AmountDiscloseAggregateVerifier.verifyProof` — called at season close for each player's reveal
- No inbox or checkpoint needed (scores go directly to contract, not via token transfer)

**New contract needed?**
- **Yes**: `LeaderboardCoordinator.sol` ~120 LOC
  - `submitScore(commitment[2], serverSig)` — stores commitment; requires a trusted game-server signature over `(player, commitment, season)` to prevent fabricated scores
  - `revealScore(publicInputs[4], proof[8])` — calls AmountDiscloseAggregateVerifier; records revealed score
  - `finalize()` — compute rankings off-chain, emit `SeasonResult(rank[], player[], score[])` event
  - **No new circuit**

**Schema for ECIES payload (app-defined)**:
- None: scores are submitted directly as commitments to the contract; no ECIES note flow needed

**Front views (if we ship)**:
- `/leaderboard/[season]` — public: ranked list (by revealed score), sealed commitments for unrevealed players
- `/leaderboard/[season]/submit` — player: receive server-signed score, submit commitment
- `/leaderboard/[season]/reveal` — player: submit amount-disclose proof at season close

**Effort estimate**:
- Contract (Solidity): ~14 hours (signature verification, phase logic, ranking emit)
- Scripts (.cjs): ~10 hours (server signing, commitment build, reveal proof, finalize)
- Frontend: 4 days

**Why it works with our stack**:
- The `AmountDiscloseAggregateVerifier` is already deployed. The commitment scheme is the same Pedersen math. The server-signature gate is the critical addition: without it, any player can claim any score by submitting a commitment to a fabricated value.

**What we'd need beyond v0.8.1**:
- `LeaderboardCoordinator.sol` (new contract, no new circuit)
- A trusted game server that signs score attestations (off-chain component)

**Risk / unknowns**:
- The server-signed score model reintroduces a central trust assumption. This is honestly a significant weakening of the ZK story — the ZK only hides the value; it does not prove the value was legitimately earned.
- Rank computation off-chain at `finalize()` is a gas optimization but adds indexer complexity.

## Demos NOT Recommended

### AlphaArena Mini (rejected)

**Idea**: trading agents with hidden positions until settlement.

**Why rejected**: positions change dynamically — open, partial close, re-enter. The accumulation model (commitment grows with each inbound transfer) does not support arbitrary state mutations. To track a changing position, the agent would need to emit a new commitment after every trade, and the verifier would need to enforce that the net commitment is consistent with the trade history. This requires either a UTXO model (unimplemented) or a complex custom circuit. Nothing in v0.8.1 supports dynamic position state natively.

---

### HiddenPackOpening (rejected)

**Idea**: Top Shot-style encrypted NFT contents revealed only after paying a reveal fee.

**Why rejected**: this requires a pay-to-reveal pattern where proof of payment unlocks an encryption key. The current stack has no key escrow primitive: there is no mechanism to release an ECIES key in exchange for a proof of payment without a trusted intermediary. Implementing this cleanly would require either a commit-reveal key escrow contract (needs careful timing analysis) or a threshold decryption scheme (not in scope). The UX is also fragile if the key holder goes offline.

---

### CommitmentMarketplace — futures/options with hidden stakes (rejected)

**Idea**: place hidden-amount bets on outcomes.

**Why rejected**: determining a winner requires comparing two hidden committed values, which the current stack cannot do without disclosure. The Pedersen commitment scheme supports homomorphic addition but not comparison. You can tally (SealedVoting), but you cannot ask "is Alice's secret value greater than Bob's secret value" without one of them revealing. A proper implementation requires range proofs (not deployed), which are a different circuit family and a mainnet-blocker.

## Privacy Limitations That Apply to All Demos

These are protocol-level constraints that all demos above must disclose honestly in their UI:

1. **Sender identity is always on-chain.** `ShieldedTransferNote` emits `from = msg.sender`. The sender's Cadence/EVM address is always public. Only amounts are hidden.

2. **Recipient identity is always on-chain.** The `to` address in `shieldedTransfer` is a public argument.

3. **Transaction timing is public.** Block timestamps are on-chain.

4. **JanusERC20/JanusFlow `totalLocked` is public.** The aggregate amount locked across all users is a public view.

5. **BabyJub pubkey is linkable.** Once a user registers their pubkey on `MemoKeyRegistry`, all transfers to them are linkable by pubkey lookup, even if the exact amounts are hidden.

These are fundamental to the commitment accumulator model. Stealth addresses and full sender-hiding are post-v0.8 roadmap items.
